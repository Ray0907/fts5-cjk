# fts5-cjk

SQLite FTS5 用の日本語・中国語・韓国語トークナイザ。C ファイル 1 つ、辞書なし、依存なし。

[English](README.md) · [繁體中文](README.zh-TW.md) · [한국어](README.ko.md)

## 問題

FTS5 に付属する 3 つのトークナイザは、どれも日本語に使えません。

- `unicode61`（デフォルト）は単語の区切りを知らないので、文全体が 1 トークンになります。`MATCH '琵琶湖'` は「滋賀県の琵琶湖は」の中を見つけられません。
- `trigram` は 3 文字単位です。「会社」「保険」のような 2 文字の単語は検索できません。
- `porter` は英語用です。

## `cjk` がすること

日本語・中国語・韓国語の連続した部分を、前後が重なる 2 文字のトークン（bigram）に分けます。Lucene の `CJKAnalyzer`、Elasticsearch の `cjk` アナライザ、Groonga のデフォルトと同じ方式です。それ以外の文字はそのまま `unicode61` に渡すので、英語の大文字小文字やアクセントの扱い、`unicode61` のオプションはすべてそのまま使えます。連続部分の最初と最後の文字は単独でも索引に登録するので、`5月` や `第38條` のように英字や数字に隣接した文字も見つかります。

```sql
.load ./cjk
CREATE VIRTUAL TABLE t USING fts5(body, tokenize='cjk');
INSERT INTO t VALUES ('琵琶湖は滋賀県にある日本最大の湖です');

SELECT * FROM t WHERE t MATCH '滋賀';        -- ヒット：部分一致
SELECT * FROM t WHERE t MATCH '滋賀 最大';   -- ヒット：2 語の AND
SELECT * FROM t WHERE t MATCH '滋賀最大';    -- ヒットしない：空白なしの 1 語は 1 つのフレーズなので、
                                            -- 滋賀 と 最大 が隣接している必要がある
SELECT highlight(t, 0, '[', ']') FROM t WHERE t MATCH '滋賀県';
-- 琵琶湖は[滋賀県]にある日本最大の湖です
```

名前の後ろの引数は `unicode61` に渡されます。

```sql
CREATE VIRTUAL TABLE t USING fts5(body, tokenize='cjk remove_diacritics 2');
```

## 検索ボックスの入力：`cjk_query()`

検索ボックスに入力された文字列をそのまま `MATCH` に渡すのは安全ではありません。`C++` は構文エラー、`勞工-退休` は列の指定と解釈され、`"` 1 つだけだと閉じていない文字列になります。この拡張は `cjk_query()` も登録しており、こうした入力を `MATCH` 用の文字列に変換します。

```sql
SELECT cjk_query('C++ 勞工-退休');   -- "C++" "勞工-退休"
SELECT cjk_query('湖');              -- "湖"*
SELECT * FROM t WHERE t MATCH cjk_query('滋賀最大', 't');
                                    -- ヒット："滋賀" "最大" に書き換え
```

- `cjk_query(text)` は ASCII の空白と全角スペース U+3000 で語に分け（U+00A0 などほかの Unicode 空白は区切りになりません）、各語をダブルクォートで囲み、CJK 1 文字だけの語には `*` を付けます。語がない入力は `""` になり、何にもヒットしません。
- `cjk_query(text, 'table')` はテーブルも参照します。1 つのフレーズとしてヒットしない CJK の語を、ヒット数が最も多い位置で分割します。まず 2 分割を試し、12 文字以下の語なら 3 分割も試します。どの分割もヒットしなければ元の語のままです。試行のたびにクエリを 1 回実行するので、分割するのは 32 文字以下の語だけで、1 回の呼び出しで試行は最大 256 回です。残りの回数で足りない語は分割しません。分割結果はテーブルの内容次第なので、同じ入力でも別のデータベースでは違う書き換えになることがあります。
- 2 引数の形は指定されたテーブルを読むため、SQLite はトリガーとビューの中での使用を拒否します。名前は 1 つの識別子としてクォートされるので、`schema.table` ではなくテーブル名を渡してください。

## ランキング：`cjk_rank_query()`

`cjk_query()` は文字列を探すためのものです。すべての語が出現する必要があり、CJK の語は書かれたとおりに出現する必要があります。質問との関連度で文書を並べるには `cjk_rank_query()` を使います。デフォルトの `cjk` テーブルがそのテキストについて索引する語を OR でつなぎます。bigram、`unicode61` の単語、そして各 CJK 連続文字列（run）の先頭文字です。先頭文字はテーブルがもともと単独で索引しています。`rank`（bm25）で並べます。

```sql
SELECT cjk_rank_query('琵琶湖の面積は');
-- "琵" OR "琵琶" OR "琶湖" OR "湖の" OR "の面" OR "面積" OR "積は"
SELECT cjk_rank_query('琵琶湖の面積は', 'edge');
-- 上と同じで、run の末尾文字 "は" も加わる
SELECT rowid FROM t WHERE t MATCH cjk_rank_query(:q) ORDER BY rank LIMIT 20;
```

| | `cjk_query()` | `cjk_rank_query()` |
|---|---|---|
| 用途 | 検索ボックス：この文字列を探す | 質問：関連度で並べる |
| 語 | AND。CJK の語は 1 つのフレーズ | OR。bigram と端の文字がそれぞれ 1 つの語 |
| 結果に含まれるもの | すべての語 | 少なくとも 1 つの語 |

[cjk-fts-bench](https://github.com/Ray0907/cjk-fts-bench) で、この関数と等価なベンチマークの Python ルールを使い、MIRACL train のクエリ（言語ごとに 100,000 パッセージ）で測定しました。これらのクエリはランキング規則や mode の選択には使っていませんが、下記の 128 語の上限はその長さから決めました。同じテーブルで `cjk_rank_query()` が返す上位 100 件はその Python ルールと一致し、`'first'` モードでは 5,657 クエリ中 5,655、`'edge'` モードではすべてで同じでした（[検証](https://github.com/Ray0907/cjk-fts-bench/blob/main/audit/rank_query_validation/summary.md)）。同じテーブルで bigram だけを OR でつないだ場合と比べ、`'first'` は nDCG@10 を 0.033（中国語）、0.021（日本語）、0.019（韓国語）上げ、いずれも 95% 信頼区間はゼロを含みません（[統計](https://github.com/Ray0907/cjk-fts-bench/blob/main/results/stats.md)）。アプリケーション側で先頭文字を加える方式（`app_bigram_first`）との差は、中国語と日本語では ±0.01 以内（0.005 と 0.007 低い）ですが、韓国語では 0.008 低く、±0.01 に収まりません。テーブルが各 run の末尾文字も同じ語として索引していることが理由と考えられますが、検証はしていません。`'edge'` はアプリケーション側で先頭と末尾を加える方式（`app_bigram_edge`）と、韓国語の 868 クエリすべてで同一、中国語では区別できず（0.0001 低い）、日本語では 0.006 低くなります。この差は有意で、文書側にあることまでは分かっていますが、原因は解明していません。この数値は 1 つの held-out 分割だけのものです。2 つ目の分割で確認されるまで、デフォルトは `'first'` です。同じテーブルで、`'edge'` は中国語で `'first'` より 0.012 高く（p=0.0002）、日本語（+0.001）と韓国語（+0.003）では ±0.01 以内ですが、下記のクエリ時間が増えます。

コストはクエリ時間で、索引サイズではありません。索引は変わりません。1 文字の語はポスティングリストが長くなります。質問 1 件あたりの平均語数（bigram のみ → `'first'` → `'edge'`）：8.8 → 9.9 → 10.9（中国語）、14.4 → 15.9 → 17.3（日本語）、12.2 → 16.7 → 21.0（韓国語）。bigram のみのクエリに対する中央値のクエリ時間（1 台のマシンで 1 回実行）：`'first'` で ×1.7、×1.2、×5.0、`'edge'` で ×2.5、×1.7、×9.6。

- デフォルトの `unigram 0` のテーブル向けです。この関数はテーブルを受け取らず、テーブルのオプションを知ることができません。`unigram 1` のテーブルではすべての文字が索引されるので、1 文字の語は run の端だけでなくすべての出現位置に一致します。その場合のランキングは測定していません。
- テキストは `unicode61` のオプションなしの `cjk` で分割されます。`remove_diacritics 0` などのオプション付きのテーブルでは、ラテン文字の語の正規化が異なることがあります。その語は一致しにくくなりますが、エラーにはなりません。
- run はトークナイザーと同じ定義です。・ と ー は run に含まれ、、。「」！ などの全角句読点で run は終わります。ベンチマークでは呼び出し前に句読点を取り除いています。
- 重複しない語は最大 128 個で、最初に出現した順です。それ以降のテキストは読みません。bm25 は重複を 2 回数えるため、同じ語は 1 回だけ並べます。上限は語の数で、バイト数ではありません。非常に長い単語も 1 つの語なので、クエリは少なくともその単語と同じ長さになります。
- テキスト中の不正な UTF-8 は、結果にも不正な UTF-8 として残ることがあります。`unicode61` が一部の不正なシーケンス（たとえばバイト列 `F4 90 80 80`）をそのまま通すためです。`MATCH` はこの結果を受け付け、文書中の同じバイト列も同じように索引されますが、テキストを厳密にデコードするドライバー（Python の `sqlite3` など）は結果を読むときにエラーになります。
- `NULL` は `NULL`、語のないテキストは `""`（何にも一致しない）を返し、`'first'`、`'edge'` 以外の mode はエラーです。
- 各語はダブルクォートで囲まれるので、入力中の演算子や引用符は文字列のままです。テーブルを読まないので、トリガーやビューの中でも使えます。

## ビルド

```sh
make        # macOS では cjk.dylib、それ以外は cjk.so
make test   # test.sql を sqlite3 で実行し、test.expected と diff
```

ビルドに必要なのは C コンパイラだけです。SQLite のヘッダは `include/` にあります。読み込みとテストには、FTS5 と拡張の読み込みに対応した `sqlite3` が必要です。macOS では Homebrew のもの（`brew install sqlite`）を使ってください。OS 付属の `sqlite3` は拡張を読み込めません。

`make asan-test` は AddressSanitizer と UBSan で拡張をビルドし、不正な UTF-8 を含むランダムなバイト列を与えます。`libsqlite3` をリンクします（macOS は Homebrew、Debian / Ubuntu は `libsqlite3-dev`）。

### 静的リンク

拡張を実行時に読み込まず SQLite をプログラムに組み込む場合は、`cjk.c` を `-DSQLITE_CORE` 付きでコンパイルし、接続を開く前に登録します。

```c
int sqlite3_cjk_init(sqlite3*, char**, const sqlite3_api_routines*);
sqlite3_auto_extension((void(*)(void))sqlite3_cjk_init);
```

```sh
cc -DSQLITE_CORE -DSQLITE_ENABLE_FTS5 app.c cjk.c sqlite3.c -lm
```

amalgamation（`sqlite3.c`）には `-DSQLITE_ENABLE_FTS5` が必要です。ないと読み込み時に `cjk: fts5 not available` になります。`make static-test` はこの方法で `test/static.c` をビルドし、`libsqlite3` とリンクします。

## 結果

### 日本語

日本語版 Wikipedia の 40 記事、4,011 段落。`tokenize=` だけが違う 3 つのテーブル。数字はクエリがヒットした段落数。`cjk` の列は全件 `LIKE '%会社%'` と完全に一致します。つまり実際にその語を含む段落の数で、他の 2 列は組み込みトークナイザがそのうち何件を見つけたかです。

| クエリ | `unicode61` | `trigram` | `cjk` |
|---|---|---|---|
| 会社 | 1 | 0 | 243 |
| 保険 | 0 | 0 | 217 |
| 労働 | 0 | 0 | 161 |
| 東京 | 16 | 0 | 560 |
| 契約 | 0 | 0 | 40 |
| 新幹線 | 367 | 379 | 379 |
| 労働基準法 | 79 | 80 | 80 |
| 東京 大学 | 0 | 0 | 262 |

`unicode61` は句読点で区切られた文節全体を 1 トークンにするので、2 文字の単語はほぼ見つかりません。`trigram` は 3 文字以上の単語なら同じ結果になりますが、2 文字の単語はゼロです。3 テーブルの構築は 1 秒未満でした。

### 中国語（繁体字）

台湾の法令データベース 47,281 条。`tokenize=` だけが違う 3 つのテーブル。数字はヒットした条文数。`bench/law.sh` で再現できます。

| 保險（保険） | 41 | 0 | 1579 |
| 特別休假（年次有給休暇） | 0 | 7 | 7 |

## 知っておくこと

- 空白なしの 1 語は 1 つのフレーズです。`MATCH '滋賀県'` は部分文字列「滋賀県」を意味します。2 語を AND したいときは空白で区切ります。
- `*` なしの 1 文字は、その文字が単独で現れる箇所か、CJK の連続部分の先頭か末尾（`5月` の「月」など）にしかヒットしません。連続部分の途中の文字は bigram の一部としてしか存在しないので、すべての出現を探すには `MATCH '湖*'` を使います。`cjk_query` は `*` を自動で付けます。`tokenize='cjk unigram 1'` ですべての文字を索引に登録することもできます（法令 4.7 万条の実測で 26.3 MB、デフォルトは 18.3 MB）。
- 下記の統一（臺→台などの異体字、全角と半角、NFD の合成）による差を除けば、2 文字以上の CJK の語と、`湖*` のように書いた 1 文字では、`cjk` の結果は `LIKE` による走査と一致します。英字と数字は従来どおり `unicode61` の語単位で一致するので、`5月` で `15月` は見つかりません。
- `+` でつないだ文字列は別々にトークン化されるので、`iphone + 手機` は `iPhone手機` を見つけません。インデックスでは 2 つの間に「手」が入るためです。`iphone手機` と 1 語で書いてください。
- `detail` はデフォルトの `'full'` のままにしてください。`detail='column'` や `detail='none'` では FTS5 がフレーズクエリを受け付けません。ここでは 3 文字以上の CJK のクエリや、CJK が英字・数字に隣接したクエリはすべてフレーズなので、`phrase queries are not supported` エラーになります。
- 全角 ASCII と半角カタカナ（濁点・半濁点を含む）、および 臺→台、裡→裏、羣→群、峯→峰、綫→線、衞→衛、爲→為、眞→真、敎→教、册→冊、祕→秘、啓→啟、淸→清、靑→青 を索引時・検索時に正規化します。その他の繁体字・簡体字変換はしません。NFD のテキスト（結合用濁点付きのかな、字母に分かれたハングル）は合成するので、NFC のクエリで見つかります。
- 索引の内容はバージョンによって変わるので、アップグレード後は既存のインデックスを再構築してください：`INSERT INTO t(t) VALUES('rebuild')`。
- 漢字、ひらがな、カタカナ、ハングル、および 々〆〇 を CJK として扱います。その他の CJK の句読点は区切りです。
- 法令 47,281 条でのインデックスサイズ：`unicode61` 11.7 MB、`cjk` 18.3 MB、`cjk unigram 1` 26.3 MB、`trigram` 27.7 MB。`cjk` は `trigram` より約 3 分の 1 小さくなります。アプリケーション側での bigram 書き換え（[cjk-fts-bench](https://github.com/Ray0907/cjk-fts-bench)）と比べると、`cjk` は run の先頭・末尾文字も索引するため転置インデックス単体は 15–60% 大きい一方、標準 FTS5 テーブルでは 12–35% 小さくなります（結果表示用に別保存する原文コピーを含めると 38–50% 小）。

## 対応する文字

| 文字 | 状態 |
|---|---|
| 日本語 | テスト済み。漢字かな混じり文、辞書不要 |
| 中国語（繁体字・簡体字） | テスト済み |
| 韓国語 | テスト済み。韓国語は分かち書きがあるので、主に名詞に付く助詞の処理に効きます |
| ラテン、キリル、ギリシャ、アラビア、ヘブライ、ベトナム語など | 従来どおり `unicode61` |
| タイ、ラオ、クメール、ビルマ、チベット文字 | 未対応。同じく分かち書きがない文字ですが、母音や声調記号が独立したコードポイントなので、書記素クラスタ単位の bigram が必要です |

## 代替

| | 方式 | 依存 |
|---|---|---|
| `cjk`（本プロジェクト） | 文字 bigram、残りは unicode61 | なし、C 570 行 |
| [wangfenjin/simple](https://github.com/wangfenjin/simple) | 1 文字単位、任意で jieba と拼音 | C++、jieba 辞書 |
| [streetwriters/sqlite-better-trigram](https://github.com/streetwriters/sqlite-better-trigram) | 漢字とかなは 1 文字単位、それ以外（ハングルを含む）は空白区切りの trigram | なし（C。SQLite の `fts5_unicode2.c` が必要） |
| [cwt/fts5-icu-tokenizer](https://github.com/cwt/fts5-icu-tokenizer) | ICU の word break iterator | ICU データ |
| 組み込み `trigram` | 文字 trigram | なし |

12 種類の構成での部分一致再現率、MIRACL ランキング、インデックスサイズ、クエリ遅延の比較は [cjk-fts-bench](https://github.com/Ray0907/cjk-fts-bench) を参照してください。

## なぜ辞書ではなく bigram か

辞書型トークナイザの品質は辞書の品質です。bigram は未知語を取りこぼしません。できないのは「滋賀最大」のような空白なしのクエリを 2 語に分けることです。FTS5 はトークナイザを呼ぶ前にフレーズ構造を決めてしまうので、この分割は FTS5 の上の層で行う必要があります。`cjk_query(text, table)` がそこで、インデックス自体を辞書として使って分割します。
